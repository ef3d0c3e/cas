Summary: The engine now builds B-spline curves exactly from control points, fits a least-squares spline to data, and picks and fits a least-squares polynomial to data or to a function, all following giac's rules. Where giac computes in doubles on exact data, ours answers exact fractions; a fit of a function answers certified decimals. Each algorithm was first prototyped in Python against giac's answers, so the Rust matched on its first CI run.

Decisions:
- Names BSpline, SplineFit, PolynomialFit; one module per family under interpolation/.
- Decimal data: exact rational of each decimal, computed exactly, answered as balls (as numdiff's convention).
- fitpoly's degree rule is decided on f64 midpoints; only the coefficients are certified.
- SplineFit with a variable uses the fit's own knots (giac uses uniform knots even with breakpoint=).
Deviations:
- fitpoly abs(x) on -1..1 moved from oracle rows to departures: giac's coefficients differ from the method's value by up to 1.3e-6.
- giac's node count is N+1 = max(64, maxdeg+2) per the source (:9625), not max(64, maxdeg+1) as the plan read it.
Findings:
- giac stddev is the population one; GSL fitspline outside the data range answers garbage (same value at 7 and -1).
- giac's gaussquad of the Chebyshev-weighted norm is inaccurate enough to change fitpoly's degree at tight tolerances (cos, tol 1e-8: 15 vs 5).
- NIntegrate's analytic tree compiles Abs; ndsolve's rhs tree does not.

## Answer

- Position: zero-based line and character. Line terminators are `\n`, `\r\n`, `\r`. "Positions are line end character agnostic." If `character` > line length, it "defaults back to the line length."
- Encodings: `utf-8`, `utf-16`, `utf-32`. Default and mandatory is `utf-16`. Negotiated via client `general.positionEncodings` (omitted = `['utf-16']`) and server `ServerCapabilities.positionEncoding` (omitted = `'utf-16'`).
- The 3.17 spec and the 3.18 draft are both silent on positions inside a surrogate pair or inside a UTF-8 sequence. The only out-of-range rule is the `character` > line-length clamp.
- Semantic token types (23) and modifiers (10) are listed below. Tokens may span lines only if `multilineTokenSupport` is set. The `overlappingTokenSupport` capability is described only as "Whether the client supports tokens that can overlap each other."
- DocumentSymbol: `name, detail?, kind, tags?, deprecated?, range, selectionRange, children?`. `selectionRange` "Must be contained by the `range`."
- SymbolKind: Function=12, Variable=13, Constant=14.
- SignatureInformation.activeParameter: `uinteger?`, "@since 3.16.0". Out-of-range or omitted: fall back to `SignatureHelp.activeParameter`, which "defaults to 0 if the active signature has parameters". ParameterInformation.label is a string or inclusive-start/exclusive-end offsets, measured in UTF-16 units.
- PrepareRename result: `Range | { range, placeholder } | { defaultBehavior: boolean } | null`. Refusal is `null` (request not valid at position) or a ResponseError with `code` and `message` ("in case the element can't be renamed"). The spec names no specific error code for this.

## Findings

(1) Position / Text Documents (Basic JSON Structures; fetched 2026-11-28)
- Position: "Position in a text document expressed as zero-based line and zero-based character offset." Also: "If the character value is greater than the line length it defaults back to the line length." Special values such as -1 for end-of-line are not supported.
- Text Documents: the protocol specifies "the following end-of-line sequences" as `\n`, `\r\n`, `\r`. "Positions are line end character agnostic." Per the fetch summary, a position cannot be between `\r` and `\n`.
- Range: start and end are both zero-based; end is exclusive.

(2) PositionEncodingKind (Text Documents, 3.17 section "Position Encodings")
- utf-8: "Character offsets count UTF-8 code units (e.g bytes)."
- utf-16: "Character offsets count UTF-16 code units." and "This is the default and must always be supported by servers".
- utf-32: "Character offsets count UTF-32 code units." Implementation note: these equal Unicode code points.
- Negotiation: "To stay backwards compatible the only mandatory encoding is UTF-16 represented via the string `utf-16`." Server reports its choice in `positionEncoding`. "If the client didn't provide any position encodings the only valid value that a server can return is 'utf-16'."
- Worked example in the spec: in `a𐐀b`, `b` is at character 3 because `𐐀` uses two UTF-16 code units.
- Mid-character positions: no sentence in 3.17 or 3.18 draft addresses a position between surrogate halves or inside a UTF-8 sequence. Design decision needed on the server side (e.g., round down to char boundary, or treat as error).

(3) Semantic tokens (Semantic Tokens section)
- SemanticTokenTypes (in order): namespace, type, class, enum, interface, struct, typeParameter, parameter, variable, property, enumMember, event, function, method, macro, keyword, modifier, comment, string, number, regexp, operator, decorator.
- SemanticTokenModifiers (in order): declaration, definition, readonly, static, deprecated, abstract, async, modification, documentation, defaultLibrary.
- SemanticTokensLegend: `tokenTypes: string[]` ("The token types a server uses.") and `tokenModifiers: string[]` ("The token modifiers a server uses.").
- multilineTokenSupport: "Whether the client supports tokens that can span multiple lines." If not supported and a token runs past line end, treat it as ending at line end.
- overlappingTokenSupport: "Whether the client supports tokens that can overlap each other."

(4) DocumentSymbol (Document Symbols section)
- Fields: name, detail?, kind, tags?, deprecated?, range, selectionRange, children?.
- selectionRange: "that should be selected and revealed when this symbol is being picked"; "Must be contained by the `range`."
- SymbolKind: Function=12, Variable=13, Constant=14.

(5) SignatureHelp / SignatureInformation / ParameterInformation (Signature Help Request)
- SignatureHelp.activeSignature: "If omitted or the value lies outside the range of `signatures` the value defaults to zero or is ignore if the `SignatureHelp` as no signatures."
- SignatureHelp.activeParameter: "If omitted or the value lies outside the range of `signatures[activeSignature].parameters`"; defaults to 0 if the active signature has parameters. Deprecated since 3.16.0 in favour of SignatureInformation.activeParameter.
- SignatureInformation.activeParameter: "The index of the active parameter." Used "in place of `SignatureHelp.activeParameter`." "@since 3.16.0".
- ParameterInformation.label: "Either a string or an inclusive start and exclusive end offsets within its containing signature label." Offsets are "based on a UTF-16 string representation as `Position` and `Range` does."

(6) Prepare Rename Request
- Result: "`Range | { range: Range, placeholder: string } | { defaultBehavior: boolean } | null`".
- `{ defaultBehavior: boolean }` (since 3.16): the rename position is valid.
- `null`: "it is deemed that a 'textDocument/rename' request is not valid at the given position."
- Error: "code and message set in case the element can't be renamed. Clients should show the information in their user interface."
- Rename Request: error "code and message set in case when rename could not be performed for any reason." (ResponseError with an appropriate message).

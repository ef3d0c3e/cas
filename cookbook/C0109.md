# eval fuzz idempotence: a limit error on re-evaluating the answer is a cache artefact, not a bug

Found at 1.8/T6 (T6.c3, Fuzz run 45802274513, eval.rs:1237-1250).
- Mechanism: memoise_warned (CAS-149) memoises a part that warned in its own rewrites for the call only, never
  stamps it. eval(e) finishes by a memo hit; eval(r) is a new call, pays the part's levels again (rule tests like
  `_?IntegerQ` re-enter the matcher on held args) and passes the recursion limit. With caches off eval(e) fails too.
- Check: replay with caches disabled (temporary env switch in a scratch build); if eval(e) also hits the limit, the
  harness is wrong, not the engine. Tolerate Recursion/Iteration/Match limits on the re-evaluation, as the
  plain-vs-traced check already does (eval.rs, "Without caches the input stops there too").
- Stamping such parts instead would reverse CAS-149's cost decision and fill MAX_WARNED: a design decision.

# C0052 — Eval fuzz plain vs traced disagree at a limit: cache order, not a bug
tags: fuzz,eval,harness,recursion-limit,cache,stamps,triage · date: 2026-11-24 · phase/task: 1.4/T9 · origin: Fuzz 45285948112, T9.c1 2a70d96

Eval fuzz parity (fuzz/fuzz_targets/eval.rs ~:1071-1093) evaluates the same input twice on one context
(plain, then traced). Caches make limit outcomes order-dependent in BOTH directions:
- plain hits a limit, traced finishes: plain's fixpoint stamps shortcut the second run (a029685).
- plain finishes, traced hits RecursionLimit: plain memoised a part (`D[1/x,x]` inside `Integrate`)
  during a shallow call that ended as a stamped fixpoint; the second run takes the stamp hit, memoises
  nothing, and evaluates the part in full deeper, past the limit (T9.c1, 2a70d96).
Triage: replay in the C0002/C0005 scratch crate; run each trace level on a FRESH context (all agree ->
not tracing); permute order on one context (order decides -> caches); run the uncached evaluator
(fails too -> the Ok was the caches' gift). Nodes are interned, so rebuilding the input keeps stamps.
Fix lives in the harness (accept a limit error on either side when the other finished), not cas-core:
making limits cache-independent would mean charging stored depth on every memo/stamp hit.

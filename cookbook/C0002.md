# C0002 — Diagnosing slow, hanging or OOM fuzz inputs
tags: fuzz,gdb,ci,debugging,timeout,oom · date: 2026-11-22 · phase/task: - · origin: gen3.2 memory ci-diagnostics-with-gdb.md

Slow, hanging or OOM fuzz input (eval target). Timing instrumentation alone can miss the spot (CAS-166: time was in
`Trace::verify`, untimed by the harness).
1. Read the timeout's own trace first (unsymbolized, `-s none`): ~100 frames alternating two return addresses = one
   function calling itself from two sites per level, an exponential double visit (CAS-176: `fold_arithmetic` folded a
   power's exponent twice). Decode the input from the log's `Output of std::fmt::Debug:` byte array (bytes → utf-8),
   look for repeated structure. Compare master's last fuzz log: `Slowest unit: N s` there = predates the change.
2. Local decode and time, no fuzzing run (CAS-516): `gh run download <run> -D .run/<phase>/art`; copy
   `fuzz/fuzz_targets/eval.rs` into a scratch bin crate (deps `arbitrary`, `cas-core` by path); replace
   `#![no_main]`/`fuzz_target!` with a `main` reading the file (`.leak()` the bytes), call `context` then
   `expr(u, 5, …)`, print both, time `ctx.eval`; `eprintln!` in `context` for rules, limits, attributes. Then
   `gdb -p <pid> -batch -ex "thread apply all bt 60"` every few seconds names the hot function.
3. OOM (CAS-201): gdb showed the spot (`ball_op` → `from_rational`) not why; temporarily instrument the suspect to
   print operands and `panic!` past a threshold (ball precision > 100000 bits): names the operand in one run.
4. On the runner only when local fails: a diag branch with a temporary `.github/workflows/diag.yml` (push-triggered
   on that branch; `cargo fuzz build --target x86_64-unknown-linux-gnu -O -a -s none eval`,
   `CARGO_PROFILE_RELEASE_DEBUG: line-tables-only`; run `-runs=1 -timeout=0` in background, `sudo gdb -p` samples).
   Pushing it is the developer's step (agents never push); its ci/fuzz runs get `gh run cancel`. Actions caches are
   branch-scoped: a diag branch cannot restore the fuzz corpus. Diag commits are never merged.
Gotchas: adding names to the eval target's BUILTINS re-maps the whole cached corpus, so a timeout right after adding
builtins is usually old slowness newly reached. `gh run view --log` is sometimes empty: use
`gh api repos/ef3d0c3e/cas/actions/jobs/<id>/logs`.

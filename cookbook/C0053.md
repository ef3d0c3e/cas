# C0053 — Per-cache-hit side data (warnings, trace steps) needs its own count bound; OOM triage via addr2line
tags: fuzz,oom,cache,memo,warnings,trace,limits,addr2line · date: 2026-11-24 · phase/task: 1.4/T9 · origin: Fuzz 45293145351, T9.c2

A memo/stamp hit is O(1) evaluation work, so no recursion/iteration/match limit counts it; an input that
rewrites into ever-nested copies of itself (fuzz: a Flat rule `k[n__] := k[…, TaylorShift[FractionMod[n],0]]`)
makes millions of hits. Anything a hit APPENDS (warnings re-given into `Warned::given`, one trace `Step`
per hit in `Tracer::record`) then grows with the hit count, not with the cache size -> OOM.
Rule: side data replayed per cache hit gets its own count bound (eval.rs `MAX_GIVEN`, mirroring
`MAX_KEPT`: compact at the bound, then grow only by new items; trace.rs `MAX_STEPS`, then `truncated`).
Diagnosis: libFuzzer `-malloc_limit_mb` OOM = one large realloc (a Vec doubling); gdb/backtrace at the
abort, or symbolize the replay's printed offsets with
`addr2line -f -C -i -e fuzz/target/x86_64-unknown-linux-gnu/release/eval <offsets>`.
Origin: Fuzz 45293145351 eval OOM, T9.c2/T9.c3.

Follow-up (T9.c4, 578f3b6): never make the bound switch the cache OFF. c2's first cut stopped memoising
warned parts past MAX_GIVEN; a native that re-evaluates its argument (TaylorShift's `coefficients` runs
Expand and Exponent again) on a self-nesting input then re-evaluated every level from scratch,
exponential (4M Exponent calls, 413 s ASAN). Fixed by keeping the per-call memo past the bound with one
representative warning (`Warned::last`), not stamping (stamps outlive the call): 0.4 s.
Triage of a slow input: log each call's input size and `sort | uniq -c` it; a few sizes repeated
millions of times means a lost cache, not an expensive call.

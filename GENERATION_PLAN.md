## Ordering rationale

- 1.1 first: safety before action, and the developer's first item. A red master hides every new failure, so each later CI check needs this green baseline; CAS-517..524 close on it. It also puts the gap script in `scripts/`, which the area phases use for their lists.
- 1.2 and 1.3 next: core before periphery. Algebra, polynomials, calculus, expressions and integers are the CAS itself (rule L1: features first), about 200 of the roughly 400 computational giac commands left in existing modules (R0-004).
- 1.4 and 1.5 follow: numerics after the symbolic core. Numerical analysis is the module CAS-517..520 opened without a design page, which 1.4's page records; 1.5 extends the existing lpsolve and nlpsolve.
- 1.6: strings and printers face the user but nothing in 1.2 to 1.5 needs them.
- 1.7: the smallest and most peripheral leftovers; its signal-processing page records CAS-521..524.
- 1.8 last: validation is its own phase, one long fuzz campaign and oracle sweeps over everything the generation added, and the gap list closes the done-criterion.
- 1.2 to 1.7 depend only on 1.1, so a reorder touches nothing else. A phase whose planner finds more than about 12 tasks splits in two through `## Changes` (risch may need this).

## Standing constraints

- Verification: tests, fuzzing and benchmarks run only on GitHub Actions; locally only `cargo check`, `cargo build` and clippy. The one local run allowed is replaying a single fuzz crash input (fuzz/README.md:98-102), under `scripts/capped.sh`. A phase's work ends with the local gate green: `cargo fmt --all --check` and CI's clippy `cargo clippy --workspace --all-targets -- -D warnings`, both with the stable toolchain's bin directory first on PATH as C0003 shows (the local default is nightly), and `cargo check --all-targets` in `fuzz/` on nightly.
- Pushing: agents never push, and work stays on master with no branches. So every phase ends with a push stop (`review: yes`: the developer pushes master), then a CI-check task. It reads CI and Fuzz on the pushed head with `gh`, one watcher per run at `--interval 60` (C0004), and greps logs through `gh api repos/ef3d0c3e/cas/actions/jobs/<id>/logs`. A red job is fixed in the same phase (a fuzz finding gets a regression test in its owning crate) and goes through another push stop. The milestone is confirmed on that green run. C0002's diagnostic branches need a push, so decode inputs locally instead.
- Developer touchpoints per phase: plan approval, one push stop at the end (more only when CI is red), the close question.
- Lific (remote, CLI with `--backend http`, never a local server): each area phase opens with its design page (`lific page create`, CAS-DOC-54 onward) and one ticket per change in the area's module (`lific issue create`). The phase plan stands in for a CAS-PLAN-n, since the CLI has no plan command. Tickets are set `done` once the phase's CI is green. Commit messages carry the ticket after the task id that `tools/commit_task.sh` prefixes (`T3.c1: CAS-531: …`).
- Names follow Xcas (`crates/cas-lang/names/en.txt`; a test checks every builtin is named or internal). CAS-DOC-7's one grammar stands: giac's alternative program syntaxes are not aliases to add.
- Numeric answers are certified balls. A departure from giac is recorded in the oracle test (the departures pattern), in crates/cas-giac/README.md ## Tests and in the area's design page. Where giac itself is wrong (bvpsolve, nlpsolve), test against closed forms or known values.
- An algorithm change updates its chapter in the same commit (crates/cas-num/doc/algorithms/, crates/cas-poly/doc/algorithms/; for cas-core natives, the module doc), with our own tricks marked with their ticket.
- Fuzz: every new builtin joins `fuzz/fuzz_targets/eval.rs` BUILTINS or a new target (with fuzz/README.md). Jobs stay within `-rss_limit_mb=2048 -malloc_limit_mb=1024`. New names remap the cached corpus, so a timeout right after an area is often old slowness newly reached (C0002).
- Rule L1: CAS-30 and every kernel speedup stay deferred. `unsafe_code = "deny"`; the one exemption is crates/cas-giac/src/library.rs.
- A brand new Lific module needs the developer's word. Existing: the card's ten plus Numerical analysis and Signal processing (Developer decides 1). Out of this generation (R0-004): units and physical constants (about 217 giac entries), graph theory (about 223), 2D, 3D and projective geometry (about 113), plotting and turtle graphics (about 121), machine learning, music and geodesy (about 17), file and terminal I/O and TI screens (about 46), and giac's alternative program syntaxes (about 80).
- Constitution: PROJECT_CONTEXT.md does not exist yet. README.md, Lific CAS-DOC-1 and docs/PRE_PA3_STATE.md stand in. The reference is giac 1.9.0 (Debian libgiac0t64 1.9.0.93), whose help database `/usr/share/giac/aide_cas` lists 1738 entries, 450 of them covered at this plan.

## Risks

- Every CI verification waits on the developer's push. While they are away, the loop waits at the push stop.
- The eval crash artifact of run 42057178575 (2026-11-05) may have expired. Then `gh workflow run fuzz.yml -f targets=eval` on the pushed master reproduces it.
- R0-004's counts are approximate (about 5 either way per area), and some leftovers are spellings of builtins we have. Each phase recomputes its list with `scripts/giac_gap.sh` and checks the near-name flags first.
- risch (1.3) and integer programming (1.5) can outgrow their phase: scope them to what giac decides, or split the phase through `## Changes`.

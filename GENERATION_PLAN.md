# Generation 2 — Frontends: a language server over the CAS, then a desktop app as its client

Goal: put the checked engine in front of users (I1): first a language server any LSP editor can use (completion, highlighting from an editor grammar plus semantic tokens, hover documentation, diagnostics, navigation; running code and listing the defined symbols through custom requests), then a desktop app that is its client and adds a view of the defined symbols and graphs, drawn from a plotting layer that builds giac's plot commands; gen 1's carry-overs (I3) close first.
Done-criteria: every phase milestone met (CI and Fuzz green on the pushed head, the phase's Lific tickets done, the app phases' screenshots reviewed by the developer); `cas-lsp` passes its protocol tests and drives a headless Neovim on CI, and its TextMate grammar and VS Code client pass their CI checks; the desktop app's CI job (unit and WebDriver end-to-end tests) is green; giac's 2D, statistics and 3D plot commands run under their giac names, each with an oracle test or a recorded departure, and the gap ledger accounts for every plotting entry; a one-hour-per-target fuzz campaign over every target, the new ones included, is green.

## Ordering rationale

- 2.1 first: safety before action. CAS-650's pattern (a native's nested evaluation gets fresh limits, so nesting costs 2^depth, C0117) is the class the fuzzer kept finding in gen 1. The plot natives of 2.6 and 2.7 evaluate user expressions at hundreds of points through the same nested evaluation, and from 2.4 on users run code interactively, where such a slowdown is a frozen editor. The other carry-overs are small engine items in the same crates; one short phase closes I3.
- 2.2 before the server: data before processing. Positions, the cursor context, the symbol index and the documentation table are knowledge of the language, so they live in cas-lang, are tested without the protocol, and keep cas-lsp a translator. The 2026-11-25 talk assumed an error-tolerant parser still had to be written; the parser already is one (CAS-DOC-7 §10, R0-001), so 2.2 is a phase of queries.
- 2.3, then 2.4: foundation before features. Editing needs no evaluation; running code adds worker threads, cancellation and session state to a server that already works.
- 2.5 before the plotting layer: the app's CI harness (WebDriver under a virtual display) is the least proven piece of the generation, and the toolkit decision rests on it. The editor, results and symbols prove it before the graph work, and the developer has a usable app halfway through.
- 2.6 and 2.7 before 2.8: data before processing; the graph view draws the plotting layer's objects. 2D first: most of giac's plot commands, and the app's first need. Two phases, because the plotting bucket (157 entries less turtle and animations) is larger than any gen 1 phase (the largest built 81 entries), and the graphic object and its sampler are new.
- 2.9 last: validation is its own phase.
- 2.1 and 2.2 depend on nothing and can swap. A phase whose planner finds more than about 12 tasks splits in two through `## Changes` (2.6 is the likeliest).

## Risks

- The app's WebDriver path (tauri-driver, WebKitWebDriver, xvfb) is the least proven link and has known Ubuntu 24.04 snags (R0-005). 2.5 proves it in its first CI runs. If it cannot be made reliable, the fallback is Playwright's WebKit driving the frontend in a browser with a test bridge to a real cas-lsp, which tests everything but the Tauri shell.
- The editor's LSP client: CodeMirror's is small, its development moved off GitHub and its feature list is unconfirmed; Monaco's is fuller but heavy. 2.5's spike settles it before the app is built on either.
- Math in WebKitGTK: its MathML may fall short on some of our export_mathml output (R0-005 found a MathML Core flag in WebKitGTK 2.51 whose default it could not confirm). KaTeX on our LaTeX is the fallback.
- WebGL under xvfb (2.8's 3D) rests on Mesa's software renderer on the runner; screenshots may come out empty, so the tests assert on data and the screenshots are for review.
- A crash in evaluation (stack overflow, abort) takes down the server, and the editor's session with it. Limits, a large worker stack and fuzzing the run path cut the risk; moving evaluation to a child process is the remedy if crashes show up.
- Plot oracles: giac's sampling and attribute words are giac's internals. Adaptive rows will be departures, and some options may resist comparison; as with risch in gen 1, scope to what giac decides and record the rest.
- CI time: every round waits about 10 minutes for CI and 45 for Fuzz, and the app job adds a cold build of the WebKitGTK bindings and the frontend. Caches (rust-cache, npm) matter; a hanging end-to-end job is cancelled and diffed as C0078 shows.
- Two ecosystems: npm brings a supply chain and churn the Rust side does not have; lockfiles, `npm ci` and few dependencies keep it small.
- The dev machine has no libwebkit2gtk-4.1-dev (checked 2026-11-27), so the app's Rust side gets no local cargo check unless the developer installs it (Developer decides 1).

## Developer decides

1. The desktop app's toolkit. Recommendation: Tauri 2, with the app's interface written in TypeScript and shown in the system's web view. It gives three hard parts ready-made: an editor that already speaks the language-server protocol (CodeMirror 6 or Monaco), display of our MathML results (WebKit renders MathML, and KaTeX can draw our LaTeX), and mature 2D and 3D plotting libraries with pan, zoom and rotate. It is also the only option whose makers document headless end-to-end tests on GitHub's Ubuntu runners (R0-005). The costs: TypeScript and npm next to Rust, WebKitGTK's quirks on Linux, and, for a local cargo check of the app, the libwebkit2gtk-4.1-dev package on your machine, which is not installed now. The alternative is egui: pure Rust and one toolchain, with egui_kittest for headless tests; but we would build the editor's completion, hover and error display, a math renderer (no mature one exists in Rust) and 3D plotting ourselves, and its image snapshots on CI's software renderer are unproven. Slint ranks with egui, and iced, GTK4 and Qt below them, all missing the same editor and math pieces (R0-005).
2. How the app is tested on CI. Recommendation, for Tauri: three layers, all on GitHub Actions and none on your machine. Unit tests of the interface's logic run with vitest, with the app's link to the server mocked. End-to-end tests start the real app with the real server under a virtual display (tauri-driver and WebKitWebDriver under xvfb on a pinned ubuntu-24.04) and check what the page shows: completion items, hover text, error marks, the results' MathML, the symbols table, and the data handed to the graphs. Each scenario also uploads a screenshot with the run, which you look at once in each app phase (2.5, 2.8, 2.9); screenshots are for your eyes, not pixel comparisons, which break on every font or WebKit update. If the WebDriver path proves unreliable, the same tests run in Playwright's WebKit against the interface alone. With egui instead, tests would use egui_kittest's simulated input and accessibility queries, with snapshots only once a software renderer works on CI.
3. New-module areas: a third new Lific module, Plotting, and R12. Recommendation: create Plotting in 2.6, and move R12's choice to generation 3. The plotting layer is engine work, over a hundred giac entries built as cas-core builtins with oracle tests like a gen 1 area, so it belongs to neither the Language server nor the Desktop app, and R5 already counted plotting among the areas that need a module of their own; without it, its tickets need an existing module, and none fits. R12, from generation 1 and still in force, says the first new-module area, graph theory or units, is chosen at generation 2; this plan makes generation 2 the frontends (R94) and adds neither, so plotting becomes generation 2's new-module area, and 2.9 corrects the gap ledger's note that the new modules come in gen 2.
4. Where the carry-overs go. R94 (in force) has the frontends start right after 1.8 with the language server first; this plan opens with 2.1, the short phase of gen 1's carry-overs. Recommendation: keep 2.1 first. It removes a slowdown the fuzzer kept finding (nested calls that cost twice as much at each level) before the server runs your code (2.4) and before the plot commands evaluate expressions at hundreds of points (2.6). If you want the frontends to start at once, 2.1 moves to just before 2.4 with no other change, since nothing depends on it but 2.9.
